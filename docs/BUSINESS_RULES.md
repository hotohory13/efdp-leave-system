# EFDP — Business Rules & Open-Decision Traceability

This is the single table future maintainers (and HR/faculty sign-off)
should check before go-live. Every row traces one assumption baked into
the Python port back to the open decision (`OD-xx`) it resolves in the
original EFSOP documents, where the default lives in code/config, and
what confirming or changing it actually requires.

| OD | Source question | Assumption shipped | Where it lives | To change it |
|----|------------------|---------------------|-----------------|--------------|
| OD-01 | Should EFDP include a daily attendance check-in/out register? | No. Official Duties (مأمورية) is the entire attendance module — advance registration, or retroactive with a written justification. There is no clock-in table. | `app/models/misc.py::OfficialDuty`, `app/services/duty_engine.py` | Would require a new `AttendanceLog` model and daily-register UI; out of scope for this port unless re-opened. |
| OD-02 | How many approval stages, and who approves at each? | Two stages: Head of Department (stage 1) → Vice Dean (stage 2), faculty-wide for stage 2 (no department scoping). | `app/models/leave.py::ApprovalRoute` (seeded rows), `app/services/leave_engine.py::STAGE_NAMES` | Add/edit rows in `approval_routes` (via Admin → Settings or a migration) and add a corresponding branch in `leave_engine._resolve_assignee`. |
| OD-03 | Does عارضة (Casual Leave) deduct from the اعتيادي (Annual) balance? | **Left "Unconfirmed" in the source workbook.** Defaulted to **No** (`CASUAL_LEAVE_DEDUCTS_FROM_ANNUAL=false`, and `LeaveType.deducts_from_annual=False` on the seeded عارضة row) to match the shipped sample data. | `.env` / `app/core/config.py::Settings.CASUAL_LEAVE_DEDUCTS_FROM_ANNUAL`, per-row override `LeaveType.deducts_from_annual` | **Must be confirmed against لائحة شؤون العاملين before production.** Flip the per-type flag via Admin → Leave Types once confirmed; no code change needed. |
| OD-03 (cont.) | What are real entitlement figures (21 annual / 6 casual)? | Placeholder values carried over verbatim from the source seed workbook. Explicitly flagged in the original docs as **not for production**. | `scripts/EFDP-LeaveTypes.xlsx`, seeded into `leave_types.annual_cap` | HR confirms real figures → update the workbook (or Admin → Leave Types) and re-run `seed_data.py` (safe: it upserts on business key). |
| OD-04 | Which public holidays count against working-day calculations? | Only Egypt's fixed-date national holidays for 2026 are seeded. Movable religious holidays (Eid al-Fitr, Eid al-Adha, Islamic New Year, Prophet's Birthday, Sham El-Nessim) are **not** included — their dates are announced by decree and cannot be predicted in advance. | `scripts/EFDP-Holidays.xlsx` (`ToAdd` sheet lists what's missing), `app/models/misc.py::HolidayCalendar`, `app/services/calendar_engine.py` | Add rows to `holidays` (Admin → Holidays) once each date is announced. The working-day *arithmetic* is correct; only the *data* is incomplete, same caveat as the original design. |
| OD-04 (cont.) | Which days are the weekend? | Friday/Saturday (Egypt working week), `WEEKEND_DAYS=4,5` (Python `weekday()`, 0=Mon). | `app/core/config.py::Settings.WEEKEND_DAYS` | Change the env var. Must agree with any external flow/spec that hardcodes weekend days — the original PowerShell/Flow specs hardcoded `(5,6)` in a different index convention; don't copy that literal. |
| OD-11 | Does the named substitute have to approve, or only be notified? | Notify only, with a right to object (`substitute_objection` free-text field) — never a blocking approval step. Submission proceeds regardless of whether the substitute has responded. | `app/models/leave.py::LeaveRequest.substitute_notified_at/substitute_objection`, `app/services/leave_engine.py::submit_leave_request` | If the faculty wants a blocking substitute-ack step, that is a new `ApprovalStep` stage, not a change to this field. |
| OD-13 | How is a retroactive (late-filed) official duty handled? | Option 2 (adopted): it is an ordinary `OfficialDuty` row with `is_retroactive=True` and a mandatory written justification (≥ `RETRO_JUSTIFICATION_MIN_LENGTH` chars), not a separate entity or workflow. | `app/models/misc.py::OfficialDuty.is_retroactive/retro_justification`, `app/services/duty_engine.py` | Adjust `RETRO_JUSTIFICATION_MIN_LENGTH` in `.env` if the minimum length needs to change. |
| BR-03 | Must a Teaching Assistant name a substitute? | Yes, mandatory; no other role is required to. Enforced at submission time, not just in the UI. | `app/services/leave_engine.py::submit_leave_request` (`EmployeeRole.TEACHING_ASSISTANT` check) | Would need a role-based rule table if this needs to extend to other roles. |
| BR-10 | Minimum content of a rejection reason. | ≥ 10 characters (`REJECTION_NOTE_MIN_LENGTH`), enforced on both leave-request and official-duty rejections. | `app/core/config.py`, `app/services/leave_engine.py`, `app/services/duty_engine.py` | Change the env var. |
| ADR-07 | How are leave balances protected from overdraft during a multi-stage approval? | Reservation model: `pending_days` is incremented at submission, converted to `used_days` only at final approval, released on rejection/cancellation. `entitled - used - pending >= 0` enforced on every mutation. | `app/models/leave.py::LeaveBalance`, `app/services/balance_engine.py` | This is a structural decision, not a config value — changing it means changing the state machine. |
| ADR-08 | How is a double-tap/duplicate submission prevented? | Idempotency key (`submission_id`, unique, client-supplied) — a repeated call with the same key returns the original request rather than creating a duplicate. | `app/models/leave.py::LeaveRequest.submission_id`, `app/services/leave_engine.py::submit_leave_request` | N/A — structural. |
| ADR-11 (parallel) | How is the acting user's identity recorded on an audit entry? | Both the claimed actor (email from the token, if ever divergent) and the resolved actor (FK to `employees.id`) are recorded, so divergence is detectable later even though only `resolved_actor_id` is populated by the current auth flow. | `app/models/misc.py::AuditLog`, `app/services/audit.py` | N/A — structural. |
| ADR-19 | How are dashboard counters computed at scale? | Precomputed nightly into `app_settings` under a `metric:` prefix by the `nightly_metrics` scheduled job, rather than aggregating the live `leave_requests` table on every page view. | `app/services/scheduler.py::nightly_metrics` | Add more `metric:` keys as new dashboard tiles are added; keep the read side (`dashboard.py`) reading from `app_settings`, not aggregating live. |
| — | Employee directory seed data. | The `Employees` sheet in the source workbook is **deliberately empty** (sample rows live on the non-imported `Example` sheet, to keep sample data from ever landing in a real deployment by accident). `seed_data.py` therefore creates **zero** employees from a production import; a `--demo` flag exists purely for local/dev convenience and must never be used against a real deployment. | `scripts/EFDP-Employees.xlsx` (`Employees` vs `Example` sheets), `scripts/seed_data.py` | HR populates the `Employees` sheet with real staff (business key: `UniversityEmail`, must match the M365 login exactly) and runs `seed_data.py` for real. |
| — | Every department needs exactly one active Head of Department, and the faculty exactly one active Vice Dean. | Not enforced by a DB constraint (a temporarily-vacant seat shouldn't be an integrity error) — checked and warned about by `seed_data.py` at the end of every run, mirroring what `05-Verify.ps1` did in the original design. | `scripts/seed_data.py::_verify_directory_health` | If this should hard-fail instead of warn, change that function. |

## Notes for whoever signs off on go-live

- Every row above marked **"Must be confirmed"** or **"not for production"**
  blocks a real launch, not a demo. The seed data is internally consistent
  and the app is fully functional against it — it is *not* validated HR
  policy.
- `docs/reference/EFSOP-Part1-Business-Analysis.md` through
  `EFSOP-Part3-Database-Design.md` and `ADR-13` through `ADR-21` remain the
  source of truth for anything not listed here; this table only covers the
  points that became a concrete assumption in code.
